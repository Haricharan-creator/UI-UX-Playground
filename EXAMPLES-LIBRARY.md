# HACHARA Examples Library

This is the baseline structure for the examples and worked-example layer. Examples should teach the user how to think, not just show a finished answer.

## Example 1 — Information Architecture

**Scenario:** A service portal contains Home, Services, Help, Account, Billing, Reports and Settings, but users repeatedly ask where to find invoices.

**What to inspect:** grouping, labels, hierarchy, findability and task language.

**Worked path:**

`User goal → current navigation → evidence → IA issue → alternative grouping → test with representative tasks → record learning`

**Illustration required:** a before/after navigation diagram with the invoice task highlighted.

## Example 2 — Dashboard hierarchy

**Scenario:** A dashboard shows 12 KPIs with equal visual weight even though only two drive the user's daily decision.

**What to inspect:** hierarchy, emphasis, grouping, scan order and progressive disclosure.

**Worked path:**

`Decision → primary KPI → supporting context → secondary details → visual hierarchy → usability check`

**Illustration required:** annotated screen showing primary, supporting and optional information.

## Example 3 — Form design

**Scenario:** A registration form asks for 14 fields before allowing the user to continue.

**What to inspect:** necessity, grouping, labels, defaults, validation, error recovery and cognitive load.

**Worked path:**

`Task → required information → optional information → field grouping → validation → test completion`

**Illustration required:** before/after form with callouts for unnecessary fields and improved error handling.

## Example 4 — Mobile responsive behaviour

**Scenario:** A desktop card layout becomes cramped on a 375px viewport.

**What to inspect:** content priority, wrapping, stacking, touch targets, navigation and overflow.

**Worked path:**

`Desktop intent → breakpoint decision → mobile information priority → layout change → interaction test`

**Illustration required:** desktop/tablet/mobile comparison.

## Example 5 — Screenshot audit

**Scenario:** A product team provides a single screenshot and asks whether the design is usable.

**What to inspect:** what the screenshot can prove versus what still requires interaction or user evidence.

**Worked path:**

`Screen evidence → heuristic/principle → finding → severity → recommendation → evidence needed to validate`

**Illustration required:** annotated screenshot with numbered findings.

## Example 6 — Good vs poor design

Every comparison should answer four questions:

1. What is different?
2. Which UX/UI principle is involved?
3. What user impact could the difference create?
4. How would we test whether the change actually helped?

Avoid declaring a design “good” only because it looks attractive. Explain the evidence and context.

## Example presentation template

For each future visual example, use:

- **Context**
- **User goal**
- **Screen / illustration**
- **What to notice**
- **Principle**
- **Why it matters**
- **Before / after**
- **Try it yourself**
- **Expected learning**
- **Validation question**

This structure keeps examples practical, evidence-based and reusable across the Classic and Modern HACHARA experiences.
