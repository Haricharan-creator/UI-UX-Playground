Designing Empty, Loading & Error States

Learn how to design system states that explain what is happening, what the person can do next, and how to recover without unnecessary confusion or dead ends.

Learn

Every state should answer the user's next question

An empty state is not automatically an error. Loading is not the same as failure. An error should not become a dead end. Good UX distinguishes these conditions and gives the person useful context and an appropriate next action.

Designer question: Can the person tell what state they are in, why it happened, whether they need to wait or act, and what happens next?
See

State-design essentials

Empty stateExplain why there is no content and, when useful, provide a meaningful first action.
Loading stateSet appropriate expectations and preserve context during waits.
Progressive loadingShow useful content as it becomes available instead of blocking unnecessarily.
Error stateExplain the problem in user-understandable language without exposing irrelevant technical detail.
RecoveryOffer a relevant next step such as retry, edit, reconnect or return to a safe point.
Preserve workAvoid destroying entered information or context when an operation fails.

Apply

Design a state system in Figma or Framer

Task

Choose one important product flow and map its normal, empty, loading, slow-loading, partial, error, retry and success states.

Deliver

Create component variants and prototype transitions. For every state, define the message, available action, preserved context and recovery destination.

Stress-test the flow with realistic failures: no data, lost connection, invalid response, timeout and interrupted submission. Check whether the user can recover without guessing.
