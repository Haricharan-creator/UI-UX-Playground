# HACHARA ARCHITECTURE LOCK v1.0

## Product principle

HACHARA is a UI/UX learning, practice, review, rework and project-development environment. It is not merely a lesson library.

## Primary product loop

**Learn → Understand → Analyse → Practice → Build → Submit → Review → Rework → Validate → Reflect → Progress**

## Primary hierarchy

**Product → Bundle → Module → Lesson → Practice → Evidence → Review → Rework → Validation → Skill/Capability**

## System layers

1. **Content layer** — lessons, examples, principles, patterns and knowledge.
2. **Curriculum layer** — bundles, modules, sequencing, prerequisites and mapping.
3. **Practice layer** — challenges, Figma/Framer tasks and real product work.
4. **Evidence layer** — links, screenshots, prototypes, observations, reflections and review records.
5. **Review layer** — UX, UI, accessibility, interaction, visual and evidence-based checks.
6. **Rework layer** — V1, feedback, reasoning, V2, validation and reflection.
7. **Progress layer** — lesson, bundle, skill, evidence and capability progression.
8. **Tool layer** — Figma, Framer and platform workflows/shortcuts.
9. **Project layer** — end-to-end real product workspace and case study.
10. **Automation layer** — inventory, mapping assistance, validation, reporting, regression and repetitive scaffolding.

## Human-control boundary

The learner/designer remains responsible for important UX decisions. HACHARA can explain, identify, question, suggest, compare and validate evidence, but must not silently replace the learner's design decisions.

## Data-driven direction

Curriculum and skill relationships should be represented as data and consumed by the application. UI pages should not become the authoritative source for curriculum structure.

## Compatibility rule

The existing application and workspace remain the implementation baseline. New architecture must be introduced incrementally and coexist with existing functionality until replacement is explicitly approved and validated.

## Automation rule

Automate repetitive work aggressively, but keep destructive operations and major curriculum decisions behind explicit human approval.

## Versioning

This architecture is v1.0. Changes require a new versioned architecture lock and a documented migration impact assessment.
